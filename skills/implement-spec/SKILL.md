Implement the supplied spec and its tickets on one **integration branch**, ready for a single pull request. Use the host's native subagents and git worktrees; Herdr is not required. Keep communication sparse: pass pointers to the spec, tickets, commits, and evidence instead of repeating their contents.

## 1. Pin the spec and task graph

Read `docs/agents/issue-tracker.md`, then use its operations to read the spec, every child ticket, and their blocking relationships. If the tracker instructions are missing, tell the user to run `/setup-supermatt-skills` in Claude linked installs or Cursor, `/supermatt:setup-supermatt-skills` from the Claude plugin, `$setup-supermatt-skills` in Codex, or `/skill:setup-supermatt-skills` in OMP, then stop. If the spec has no implementation tickets, tell the user to run `/to-tickets` in Claude linked installs or Cursor, `/supermatt:to-tickets` from the Claude plugin, `$to-tickets` in Codex, or `/skill:to-tickets` in OMP, then stop.

Build a **task graph** with ticket states `pending`, `running`, `integrated`, and `blocked`. Keep it with the worker assignments, branch names, commit SHAs, evidence paths, and dispatch snapshot in an OS temporary directory outside the repository. A closed ticket counts as integrated only after verifying its implementation is in the integration branch. Surface contradictory criteria before implementation. An open blocker outside this spec stays blocked until its work is merged into the default branch; a dependency cycle needs a user decision.

The **frontier** contains pending tickets whose prerequisites are all present on the integration branch. Within this run, a ticket becomes integrated after step 3 verifies its merge. That makes its dependents eligible even though its tracker issue stays open. An empty frontier with unfinished tickets and no running worker is blocked, not complete: report the blocking edges and stop.

## 2. Prepare the integration branch

Discover the default branch and record its current commit as `BASE`, the fixed point for final QA and review. Create a branch from it using the repository's naming convention in a dedicated worktree. Preserve the caller's existing work and branches. If the user supplied an existing integration branch, inspect it, record its merge-base with the default branch as `BASE`, and reconcile the graph against its actual commits before assigning work.

Create each worker's worktree on its own new branch from the current integration tip. Verify that starting commit before dispatch; if the base is wrong, preserve the worktree and correct the assignment instead of resetting existing work. Respect the host's available subagent slots. Without subagents, work one ticket at a time using the same worktree and verification steps.

Prepare every worktree this run creates before any agent works in it: the integration worktree, each worker worktree, and any worktree made later for QA or a fix. After verifying its starting commit, run the repository's setup from the worktree root, reading the setup source from that worktree's own files. When the per-repository setup document `docs/agents/worktree-setup.md` exists, its ordered shell commands replace any setup the repository's other docs describe. Otherwise use the setup documented in `AGENTS.md`, or failing that in `README.md`, or failing that in `CONTRIBUTING.md`. A check, such as a test or lint command, is not setup. When none of them documents a setup, record that no setup was found and dispatch without one. With either source, the setup includes the submodule steps that it or the repository's required checks depend on: initialize each submodule they use and check it out at the commit the worktree records (`git submodule update --init`), and when one of them reads a submodule's tags (such as `git describe --tags`), make that lookup work. A `shallow = true` entry in `.gitmodules` leaves out the tags and the history that reaches them, so fetch both (for example `git -C <submodule> fetch --tags --unshallow`), then run the lookup to confirm it.

Worktrees share the main worktree's Git hooks, and an install can run a `prepare` script that rewrites them. Before each setup run, record, from the main worktree (the first entry of `git worktree list`), the hooks directory that `git rev-parse --path-format=absolute --git-path hooks` prints and, for each entry in it, its type, mode, and content digest (for example `ls -l` and `shasum -a 256`; timestamps are not compared). After the setup, record them again and compare. Any difference, a lost executable bit included, stops the run before that dispatch: dispatch and merge nothing more, report each hook file added, changed, or removed, and leave them for the user without restoring them.

Setup succeeds when every command exits zero, every tag lookup it confirms works, and the hooks are unchanged. A failed setup is the coordinator's to resolve, never an agent's: fix its cause outside the repository's files, such as a missing tool or an unreachable registry, and rerun it; report a failure that persists to the user. Dispatch no agent into a worktree whose setup has not succeeded: record the failing command and its output as the reason, and keep its ticket `blocked` until a rerun succeeds. A successful setup's **leftover paths** are those `git status --porcelain=v1 --untracked-files=all --ignore-submodules=none` lists after it ran with a status line, staged or unstaged diff, or untracked content that differs from just before it ran; a path the setup made clean is not one. Record the leftover paths and ask the user how to treat them before the run goes on; do not delete, ignore, or commit them yourself. Record each worktree's setup source, outcome, and hooks comparison with the task graph.

## 3. Build and integrate the frontier

Before the first dispatch, record a **dispatch snapshot** of the coordinator's starting checkout and of the integration worktree with the task graph: each one's `HEAD`, its `git status --porcelain=v1 --untracked-files=all --ignore-submodules=none` output, a digest of its staged diff (`git diff --cached --binary --no-ext-diff --no-textconv --ignore-submodules=none`) and of its unstaged diff (the same command without `--cached`), and a content digest of each untracked file. Those flags keep a configured diff helper or a submodule's `ignore` setting from hiding a change. A command that fails records no snapshot, and during a check it stops integration. A shared starting checkout may already be dirty: only changes since the snapshot count. Before each later dispatch, each merge-slot integration, and final QA, run the **snapshot check**. The starting checkout must match its whole snapshot. The integration worktree must match its snapshot's status and digests, and its `HEAD` must equal its expected tip: the commit it started from, or the last one this run merged there. Any difference stops integration. Report the changed paths and leave them in place: do not commit, discard, stash, or re-apply them, though you may save a copy outside the repository for attribution. Record a new snapshot only after the user settles the difference, or after a merge as described below.

Before dispatching parallel workers, read [Parallel resources](../../references/parallel-resources.md) and record their resource ownership with the task graph. Dispatch frontier tickets only where their edits and mutable resources can proceed independently. Give each implementer its ticket, relevant spec sections, the absolute path of its worktree, starting SHA, resource assignment, setup source, and this contract:

- Work only in the assigned worktree. Every path passed to any tool, reads included, and every shell working directory is absolute and under that worktree: on some hosts a subagent starts in the coordinator's directory, so a relative path lands in another checkout. The only other allowed paths are installed skill resources, for reading, and OS temporary directories that an agent or its loaded skills create for scratch work and evidence. The coordinator's starting checkout and the integration worktree are read-only. Hand this rule, with the absolute worktree path, to every subagent you dispatch, read-only scouts, QA readers, and reviewers included, and require each to hand it on to its own subagents. Report any other write found outside the worktree by its paths instead of cleaning it up.
- The worktree is already prepared: the coordinator ran the setup from the given source there, or found none documented, and reruns it when a sync needs it, so do not repeat it. A setup gap you find goes in your report.
- Load and follow the `tdd` skill through the host's skill mechanism at the agreed test seams. For a refactor without tests, first pin current behavior with characterization tests in a separate commit.
- Use focused checks during TDD cycles. Before committing a completed behavior, complete the repository's full required gate. Reuse passing checks only when their relevant files, dependencies, configuration, and environment are unchanged.
- Commit the completed work with the ticket reference. Report the commit SHA, acceptance-criterion coverage, check results, evidence paths, and any unresolved question. Leave tracker issues open and let the coordinator integrate the branch.

The coordinator owns a **single merge slot**. When a worker finishes, hold that slot while it brings the latest integration tip into its branch. Resolve conflicts by loading and following the `resolving-merge-conflicts` skill through the host's skill mechanism in that worktree. When the sync changed the **setup inputs** (the setup source, a dependency manifest or lockfile, `.gitmodules`, or a submodule's pinned commit), rerun the setup in that worktree from its synced files, with the same hooks guard and success rule. Then rerun checks invalidated by the merge, including the full required gate on the combined code. A failed check or unresolved question keeps the ticket out of the integration branch.

Wait for the worker and its subagents to finish writing, then run the snapshot check. In the integration worktree, merge the verified worker commit with `git merge --ff-only`. If the integration tip advanced, sync and verify the worker again before retrying; never force the branch forward. Verify that the reported commit is now an ancestor of the integration tip, record its evidence, and mark the ticket integrated. Still holding the slot, when the merge changed the setup inputs, rerun the setup in the integration worktree the same way; until it succeeds and the user settles its leftover paths, dispatch nothing and hold step 4. Then record a new snapshot of the integration worktree, so what the merge itself changed, such as a moved submodule pin or a newly ignored file, does not stop a later check, and release the merge slot. Recompute the frontier and dispatch newly eligible tickets. A merge into this branch does not close a tracker issue.

After the first successful merge, open a draft PR only if the tracker closes work through PRs or the user requested one. Target the default branch, reference the spec and all tickets it will finish, and load and follow the `pr` skill through the host's skill mechanism for the body. Keep one PR for the integration branch. Without a PR, retain the branch for the later shipping step.

## 4. Verify the whole spec

Once every ticket is integrated, run the snapshot check, then the repository's full required gate on the final integration commit, reusing unchanged valid results. Then run these checks in order:

For independently evolving providers and consumers, first identify the spec's authoritative contract and owner. Check actual serialized responses and consumer fixtures against that same artifact, including relevant errors, null values, mocks, and feature-flag paths. A matching mock or separately declared type alone does not verify the boundary. Missing ownership or contradictory contracts leave the affected acceptance criteria unresolved. Components changed and built atomically can use their existing shared type; add no contract tool without a demonstrated gap.

1. In a fresh subagent, load and follow the `qa` skill through the host's skill mechanism against `BASE` and the whole spec, including cross-ticket behavior. Give it the integration worktree's absolute path under the workers' path rule. Pass working preview details and tell it to report without editing the repository or tracker. Without subagents, run QA yourself and state the independence limit. Fix each fail through `tdd`, commit, and repeat QA with the prior report, tested SHA, and fix diff. Keep evidence in the OS temporary directory.
2. Load and follow the `code-review` skill through the host's skill mechanism against `BASE`, with the whole spec, ticket references, and the integration worktree's absolute path as every reader's root under the workers' path rule. Wait for its aggregate verdict; an individual reader's output is not the final review.
3. Resolve every verified finding at every severity. Fix behavior changes through "tdd" and keep behavior-preserving refactors separate. A fix that contradicts the spec or needs an external change goes to the user; a finding is settled only by a fix or an explicit user decision. Complete the required gate for fixes, run follow-up QA for affected behavior, then follow-up "code-review" from the last reviewed commit with the prior reports. Retain valid evidence for unaffected behavior; a test-only fix does not require fresh browser QA.

Ready means the entire spec is integrated, required checks pass, QA has no fails or blocked scenarios, every review axis completed, and every verified finding is fixed or explicitly settled by the user. If a check cannot run or work remains blocked, retain the draft state and report the exact gap. Update the PR evidence with the final commit and verdicts before marking it ready.

## 5. Hand off and clean up

Leave the integration branch, its worktree, and any PR available for shipping. Keep the spec and ticket issues open until the work merges into the default branch. When ready, tell the user to run `/ship-pr` in Claude linked installs or Cursor, `/supermatt:ship-pr` from the Claude plugin, `$ship-pr` in Codex, or `/skill:ship-pr` in OMP. This skill does not invoke that user-only skill or merge the PR.

Before removing a worker worktree, retain its reports and session references, confirm the worker and its subagents have exited, verify a clean tree (`git status --porcelain=v1 --untracked-files=all --ignore-submodules=none` prints nothing, whatever a submodule's `ignore` setting says), and verify all its commits are reachable from, or patch-equivalent to, the integration branch: `git cherry <integration branch> <worker branch>` prints no `+` line. `git cherry` skips merge commits, so each merge that the integration branch does not reach (`git rev-list --merges <integration branch>..<worker branch>`) must record exactly what Git's automatic merge of its parents produces: `git show --remerge-diff --ignore-submodules=none --no-ext-diff --no-textconv --format= <merge>` prints nothing, so a `diff.ignoreSubmodules` setting cannot hide a submodule pin the merge moved. A conflict resolution, or a merge that drops one parent's change, is in no patch; a combined diff (`git diff-tree --cc`) misses a hunk that keeps one parent's side. A rebase of the integration branch, for example onto an advanced default branch, leaves no worker commit reachable from it, yet each patch is still there. Check against the integration branch, never the default branch: once the integration branch ships by squash merge, its commits are no longer patch-equivalent to the default branch. Remove only worktrees created by this run that meet those conditions, with `git worktree remove` and no `--force`.

Git refuses that removal for any worktree holding a submodule repository, even a clean or deinitialized one (`working trees containing submodules cannot be moved or removed`), and `--force` deletes those repositories with the worktree. After that refusal, run `git -C <worktree> submodule absorbgitdirs`, which moves each submodule repository embedded in the worktree, nested ones included, into its modules directory. It leaves a repository that a `.git` file points to elsewhere, and one a deinitialized or removed submodule left behind, so confirm that no Git repository remains inside the worktree directory, whatever its name: for each path `find <worktree> -name HEAD` prints, a file or a symbolic link alike, `git --git-dir=<its directory> rev-parse --git-dir` fails. Then rerun the removal with `--force` only when the worktree also passes these checks:

- `git submodule status --recursive` shows no `+` or `U` prefix, so each initialized submodule sits at the commit the worker branch records. A deinitialized submodule (`-`) goes on to the next check, because its repository stays behind.
- No commit exists only in this worktree's submodule repositories. For each repository under the worktree's modules directory (`git -C <worktree> rev-parse --git-path modules`), nested, deinitialized, and removed ones included, list the commits that no remote-tracking ref contains: `git --git-dir=<repository> --work-tree=<repository> rev-list <pinned commit> --all --reflog --not --remotes`. The listing keeps commits that only a local tag or a reflog holds, since both go with the worktree. Pass the pinned commit `git submodule status --recursive` shows for that submodule, and none for a repository it no longer lists, such as one the worker branch removed with `git rm`; `--work-tree` keeps Git from entering a submodule directory that no longer exists. Each listed commit must also be held by the repository at the same relative path under the main worktree's modules directory (`git -C <main worktree> rev-parse --git-path modules`, the main worktree being the first entry of `git worktree list`): `git --git-dir=<that repository> --work-tree=<that repository> rev-list --all --reflog` lists it.

Retain every other worktree, including one where a check's command fails, and name it in the handoff with the check it failed and any commit that exists only there. Apply the same lifecycle rule when a run stops early.

Report the integration branch and commit, PR URL if any, integrated and blocked tickets, QA and review verdicts, retained evidence, and worktrees that remain. Before the user clears the session, recommend `/retro` in Claude linked installs or Cursor, `/supermatt:retro` from the Claude plugin, `$retro` in Codex, or `/skill:retro` in OMP, or pass the session logs for a later retrospective.
