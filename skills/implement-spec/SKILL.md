Implement the supplied spec and its tickets on one **integration branch**, ready for a single pull request. Use the host's native subagents and git worktrees; Herdr is not required. Keep communication sparse: pass pointers to the spec, tickets, commits, and evidence instead of repeating their contents.

## 1. Pin the spec and task graph

Read `docs/agents/issue-tracker.md`, then use its operations to read the spec, every child ticket, and their blocking relationships. If the tracker instructions are missing, tell the user to run `/setup-supermatt-skills` in Claude linked installs or Cursor, `/supermatt:setup-supermatt-skills` from the Claude plugin, `$setup-supermatt-skills` in Codex, or `/skill:setup-supermatt-skills` in OMP, then stop. If the spec has no implementation tickets, tell the user to run `/to-tickets` in Claude linked installs or Cursor, `/supermatt:to-tickets` from the Claude plugin, `$to-tickets` in Codex, or `/skill:to-tickets` in OMP, then stop.

Build a **task graph** with ticket states `pending`, `running`, `integrated`, and `blocked`. Keep it with the worker assignments and the contract each worker was given, branch names, commit SHAs, evidence paths, push records, and dispatch snapshot in the **run directory** `${XDG_STATE_HOME:-$HOME/.local/state}/implement-spec/<repo-key>/<spec-key>/`, outside the repository. Unlike the OS temporary directory, it survives a host reboot, so the run's state, contracts, and evidence stay readable after a crash; scratch copies can still live in the OS temporary directory. A run directory left by an earlier run of this spec is that run's state: reconcile it against the actual branches and commits instead of overwriting it. A closed ticket counts as integrated only after verifying its implementation is in the integration branch. Surface contradictory criteria before implementation. An open blocker outside this spec stays blocked until its work is merged into the default branch; a dependency cycle needs a user decision.

Use full SHA-256 hex digests of UTF-8 identity strings for `<repo-key>` and `<spec-key>`, not basenames or slash replacement. The repository identity is its canonical remote service host and full project path, independent of SSH or HTTPS spelling and a trailing `.git`; with no remote, use the canonical absolute path of its common Git directory, shared by linked worktrees. The spec identity is `issue:` followed by the full tracker reference (service, project, and issue ID), or `file:` followed by the normalized repository-relative spec path with `/` separators, including its feature directories. Record both identity strings and the resolved run directory with the task graph; reuse them on resume, including from another linked worktree. Before reusing existing state, confirm both recorded identities match the requested repository and spec; a mismatch stops the run with both identities reported and the directory left unchanged.

The **frontier** contains pending tickets whose prerequisites are all present on the integration branch. Within this run, a ticket becomes integrated after step 3 verifies its merge. That makes its dependents eligible even though its tracker issue stays open. An empty frontier with unfinished tickets and no running worker is blocked, not complete: report the blocking edges and stop.

## 2. Prepare the integration branch

Discover the default branch and record its current commit as `BASE`, the fixed point for final QA and review. Create a branch from it using the repository's naming convention in a dedicated worktree. Preserve the caller's existing work and branches. If the user supplied an existing integration branch, inspect it, record its merge-base with the default branch as `BASE`, and reconcile the graph against its actual commits before assigning work.

Create each worker's worktree on its own new branch from the current integration tip. Verify that starting commit before dispatch; if the base is wrong, preserve the worktree and correct the assignment instead of resetting existing work. Respect the host's available subagent slots. Without subagents, work one ticket at a time using the same worktree and verification steps.

Prepare every worktree this run creates before any agent works in it: the integration worktree, each worker worktree, and any worktree made later for QA or a fix. After verifying its starting commit, run the repository's setup from the worktree root, reading the setup source from that worktree's own files. When the worktree has a `.tern/worktree.json` and `command -v tern-wt` finds tern-worktrees, the setup is `tern-wt prepare <worktree>`: it starts the host services that file shares between worktrees, then runs its setup commands to completion, and a nonzero exit is a failed setup with the error code, command, and output it reports. Heavy commands in that worktree then follow [Parallel resources](../../references/parallel-resources.md). Otherwise, when the per-repository setup document `docs/agents/worktree-setup.md` exists, its ordered shell commands replace any setup the repository's other docs describe. Otherwise use the setup documented in `AGENTS.md`, or failing that in `README.md`, or failing that in `CONTRIBUTING.md`. A check, such as a test or lint command, is not setup. When none of them documents a setup, record that no setup was found and dispatch without one. With either source, the setup includes the submodule steps that it or the repository's required checks depend on: initialize each submodule they use and check it out at the commit the worktree records (`git submodule update --init -- <path>`), and when one of them reads a submodule's tags (such as `git describe --tags`), make that lookup work. A `shallow = true` entry in `.gitmodules` leaves out the tags and the history that reaches them, so fetch both (for example `git -C <submodule> fetch --tags --unshallow`), then run the lookup to confirm it.

Worktrees share the main worktree's Git hooks, and an install can run a `prepare` script that rewrites them. Before each setup run, record the worktree's own state with the dispatch snapshot commands of step 3, and record, from the main worktree (the first entry of `git worktree list`), the hooks directory that `git rev-parse --path-format=absolute --git-path hooks` prints and, for each entry in it, its type, mode, and content digest (for example `ls -l` and `shasum -a 256`; timestamps are not compared). After the setup, record both again and compare. Any hooks difference, a lost executable bit included, stops the run before that dispatch: dispatch and merge nothing more, report each hook file added, changed, or removed, and leave them for the user without restoring them.

Setup succeeds when every command exits zero, every tag lookup it confirms works, and the hooks are unchanged. A failed setup is the coordinator's to resolve, never an agent's: fix its cause outside the repository's files, such as a missing tool or an unreachable registry, and rerun it; report a failure that persists to the user. Dispatch no agent into a worktree whose setup has not succeeded: record the failing command and its output as the reason, and keep its ticket `blocked` until a rerun succeeds. A successful setup's **leftover paths** are those whose status line, staged or unstaged diff, or untracked content differs between the worktree records taken just before and just after it, a path that appears or disappears included, except a tracked path the setup restored to its committed content, such as a submodule checked out at its pin. Record the leftover paths and ask the user how to treat them before the run goes on; do not delete, ignore, or commit them yourself. Record each worktree's setup source, outcome, and hooks comparison with the task graph.

## 3. Build and integrate the frontier

Before the first dispatch, record a **dispatch snapshot** of the coordinator's starting checkout and of the integration worktree with the task graph: each one's `HEAD`; its `git status --porcelain=v1 -z --untracked-files=all --ignore-submodules=none` output, whose NUL-separated entries give each path unquoted, a rename entry carrying its source path as well; a digest of its whole staged diff (`git diff --cached --binary --no-ext-diff --no-textconv --ignore-submodules=none`) and of its whole unstaged diff (the same command without `--cached`); the same two digests for each tracked path listed, taken with `git --literal-pathspecs diff` and the path passed as one quoted argument after `--`, so each difference can be named; and a content digest of each untracked file. Those flags keep a configured diff helper, a submodule's `ignore` setting, or a file name read as a pathspec from hiding a change. A command that fails records no snapshot, and during a check it stops integration. A shared starting checkout may already be dirty: only changes since the snapshot count. Before each later dispatch, each merge-slot integration, and final QA, run the **snapshot check**. The starting checkout must match its whole snapshot. The integration worktree must match its snapshot's status and digests, and its `HEAD` must equal its expected tip: the commit it started from, or the last one this run merged there. Any difference stops integration. Report the changed paths and leave them in place: do not commit, discard, stash, or re-apply them, though you may save a copy outside the repository for attribution. Record a new snapshot only after the user settles the difference, or after a merge as described below.

Before dispatching parallel workers, read [Parallel resources](../../references/parallel-resources.md) and record their resource ownership with the task graph. Dispatch frontier tickets only where their edits and mutable resources can proceed independently. Give each implementer its ticket, relevant spec sections, the absolute path of its worktree, starting SHA, resource assignment, setup source, the absolute path of its **evidence directory** (`evidence/<ticket>/` in the run directory), and this contract:

- Work only in the assigned worktree. Every path passed to any tool, reads included, and every shell working directory is absolute and under that worktree: on some hosts a subagent starts in the coordinator's directory, so a relative path lands in another checkout. The only other allowed paths are installed skill resources, for reading, the assigned evidence directory, for writing evidence, and OS temporary directories that an agent or its loaded skills create for scratch work and evidence. The coordinator's starting checkout and the integration worktree are read-only. Hand this rule, with the absolute worktree and evidence directory paths, to every subagent you dispatch, read-only scouts, QA readers, and reviewers included, and require each to hand it on to its own subagents. Report any other write found outside the worktree by its paths instead of cleaning it up.
- The worktree is already prepared: the coordinator ran the setup from the given source there, or found none documented, and reruns it when a sync needs it, so do not repeat it. A setup gap you find goes in your report.
- Load and follow the `tdd` skill through the host's skill mechanism at the agreed test seams. For a refactor without tests, first pin current behavior with characterization tests in a separate commit.
- Use focused checks during TDD cycles. Before committing a completed behavior, complete the repository's full required gate. Reuse passing checks only when their relevant files, dependencies, configuration, and environment are unchanged.
- Commit the completed work with the ticket reference. Keep every piece of evidence you report, your subagents' included, in the evidence directory: copy it there from an OS temporary directory before reporting, since a host reboot wipes that one. Report the commit SHA, acceptance-criterion coverage, check results, evidence paths, and any unresolved question. Leave tracker issues open and let the coordinator integrate the branch.

The coordinator owns a **single merge slot**. When a worker finishes, hold that slot while it brings the latest integration tip into its branch. Resolve conflicts by loading and following the `resolving-merge-conflicts` skill through the host's skill mechanism in that worktree. When the sync changed the **setup inputs** (the setup source, a dependency manifest or lockfile, `.gitmodules`, or a submodule's pinned commit), rerun the setup in that worktree from its synced files, with the same hooks guard and success rule. Then rerun checks invalidated by the merge, including the full required gate on the combined code. A failed check or unresolved question keeps the ticket out of the integration branch.

Wait for the worker and its subagents to finish writing, then run the snapshot check. In the integration worktree, merge the verified worker commit with `git merge --ff-only`. If the integration tip advanced, sync and verify the worker again before retrying; never force the branch forward. Verify that the reported commit is now an ancestor of the integration tip, record its evidence, and mark the ticket integrated. Still holding the slot, when the merge changed the setup inputs, rerun the setup in the integration worktree the same way; until it succeeds and the user settles its leftover paths, dispatch nothing and hold step 4. After every merge, compare the integration worktree with its pre-merge snapshot path by path. A difference stops integration like any snapshot-check difference, unless its path is one the merge changed (`git diff --name-only --no-renames --ignore-submodules=none <previous tip> <new tip>`) that now shows no change, or only a submodule still checked out at the commit it had before the merge (its `git diff --ignore-submodules=none -- <path>` shows that commit as the checkout); one whose ignore status the merged `.gitignore` changed; one the rerun restored to its committed content; or a leftover path the user settled. Otherwise record a new snapshot of the integration worktree and release the merge slot. Recompute the frontier and dispatch newly eligible tickets. A merge into this branch does not close a tracker issue.

**Backup pushes.** A commit that exists only in local worktrees is lost when a host crash corrupts or wipes them, so push each worker branch once its commit is verified (synced, gate green, snapshot check passed), and the integration branch after each verified merge and each step 4 fix commit, when a push of that branch starts no CI run. Check that for each branch before its first push, again for the integration branch once a PR is open for it, and again after a merge or fix changes the CI configuration. For GitHub Actions, read every workflow in `.github/workflows/`, on the pushed commit and on the default branch, and confirm that no trigger fires on that push: no `push` trigger whose filters admit the branch (one with no filter admits every branch, one with only `tags` or `tags-ignore` admits none), no `create` trigger for the push that creates the branch, and, with a PR open, no `pull_request` or `pull_request_target` trigger that admits its base. Other CI services have their own trigger settings; a trigger you cannot rule out counts as one that fires. Record each answer and its source in the run directory. Push plainly to the remote the integration branch will ship from, never with force; a rejected push is recorded and reported, not retried with force. When a push would start CI, or the triggers cannot be read, push nothing and record each commit that exists only locally, so the handoff names it.

After the first successful merge, open a draft PR only if the tracker closes work through PRs or the user requested one. Target the default branch, reference the spec and all tickets it will finish, and load and follow the `pr` skill through the host's skill mechanism for the body. Keep one PR for the integration branch. Without a PR, retain the branch for the later shipping step.

## 4. Verify the whole spec

Once every ticket is integrated, run the snapshot check, then the repository's full required gate on the final integration commit, reusing unchanged valid results. Then run these checks in order:

For independently evolving providers and consumers, first identify the spec's authoritative contract and owner. Check actual serialized responses and consumer fixtures against that same artifact, including relevant errors, null values, mocks, and feature-flag paths. A matching mock or separately declared type alone does not verify the boundary. Missing ownership or contradictory contracts leave the affected acceptance criteria unresolved. Components changed and built atomically can use their existing shared type; add no contract tool without a demonstrated gap.

1. In a fresh subagent, load and follow the `qa` skill through the host's skill mechanism against `BASE` and the whole spec, including cross-ticket behavior. Give it the integration worktree's absolute path under the workers' path rule. Pass working preview details and tell it to report without editing the repository or tracker. Without subagents, run QA yourself and state the independence limit. Fix each fail through `tdd`, commit, and repeat QA with the prior report, tested SHA, and fix diff. QA keeps its evidence in its own temporary directory, so after each QA report copy the evidence it cites into `evidence/qa/` in the run directory, where a reboot does not wipe it, and record those paths.
2. Load and follow the `code-review` skill through the host's skill mechanism against `BASE`, with the whole spec, ticket references, and the integration worktree's absolute path as every reader's root under the workers' path rule. Wait for its aggregate verdict; an individual reader's output is not the final review.
3. Resolve every verified finding at every severity. Fix behavior changes through "tdd" and keep behavior-preserving refactors separate. A fix that contradicts the spec or needs an external change goes to the user; a finding is settled only by a fix or an explicit user decision. Complete the required gate for fixes, run follow-up QA for affected behavior, then follow-up "code-review" from the last reviewed commit with the prior reports. Retain valid evidence for unaffected behavior; a test-only fix does not require fresh browser QA.

Ready means the entire spec is integrated, required checks pass, QA has no fails or blocked scenarios, every review axis completed, and every verified finding is fixed or explicitly settled by the user. If a check cannot run or work remains blocked, retain the draft state and report the exact gap. Update the PR evidence with the final commit and verdicts before marking it ready.

## 5. Hand off and clean up

Leave the integration branch, its worktree, and any PR available for shipping. Keep the spec and ticket issues open until the work merges into the default branch. When ready, tell the user to run `/ship-pr` in Claude linked installs or Cursor, `/supermatt:ship-pr` from the Claude plugin, `$ship-pr` in Codex, or `/skill:ship-pr` in OMP. This skill does not invoke that user-only skill or merge the PR.

Before removing a worker worktree, retain its reports and session references, confirm the worker and its subagents have exited, verify a clean tree (`git status --porcelain=v1 --untracked-files=all --ignore-submodules=none` prints nothing, whatever a submodule's `ignore` setting says), and verify all its commits are reachable from, or patch-equivalent to, the integration branch: `git cherry <integration branch> <worker branch>` prints no `+` line. `git cherry` skips merge commits, so each merge that the integration branch does not reach (`git rev-list --merges <integration branch>..<worker branch>`) must record exactly what Git's automatic merge of its parents produces: `git show --remerge-diff --ignore-submodules=none --no-ext-diff --no-textconv --format= <merge>` prints nothing, so a `diff.ignoreSubmodules` setting cannot hide a submodule pin the merge moved. A conflict resolution, or a merge that drops one parent's change, is in no patch; a combined diff (`git diff-tree --cc`) misses a hunk that keeps one parent's side. A rebase of the integration branch, for example onto an advanced default branch, leaves no worker commit reachable from it, yet each patch is still there. Check against the integration branch, never the default branch: once the integration branch ships by squash merge, its commits are no longer patch-equivalent to the default branch. Remove only worktrees created by this run that meet those conditions, with `git worktree remove` and no `--force`.

When Git refuses that removal, read and follow [Worktree removal with submodules](../../references/worktree-removal.md): it decides whether a clean worktree that holds submodule repositories may be removed with `--force`.

Retain every other worktree, including one where a check's command fails, and name it in the handoff with the check it failed and any commit that exists only there. Apply the same lifecycle rule when a run stops early.

Report the integration branch and commit, PR URL if any, integrated and blocked tickets, QA and review verdicts, the run directory and the evidence retained in it, worktrees that remain, the worker branches this run pushed, and each commit that exists only locally. Keep the run directory after the handoff: it is the record a later session or retrospective reads. Before the user clears the session, recommend `/retro` in Claude linked installs or Cursor, `/supermatt:retro` from the Claude plugin, `$retro` in Codex, or `/skill:retro` in OMP, or pass the session logs for a later retrospective.
