# Verify a spec (session V)

A spec is a parent issue: its tickets are its sub-issues, or the issues whose `## Parent` section names it. For local Markdown, it is the `spec.md` beside the feature's `issues/` directory. Once the last ticket closes, check that the tickets together delivered what the spec asked for.

1. Show phase `verify`. Start the worker.
2. Use [Send the prompt](WORKER.md#dispatch-preamble) for each task below (`--wait`, no timeout), waiting for each reply before the next:
   - `Verify spec REF: all of its tickets are closed. Establish FIXED_POINT as the parent of the oldest commit on DEFAULT that references one of its tickets. Use GitHub numbers or repository-relative local ticket paths as appropriate. Return the full commit SHA and supporting commit/ticket evidence. Leave the repository and tracker unchanged.` Retain that evidence in lane state. If the fixed point cannot be established, park with the missing evidence.
   - `Load and follow the qa skill through the host's skill mechanism, with FIXED_POINT as the fixed point and REF as the spec.` Substitute the resolved SHA and spec and include the fixed-point evidence. Append: `This is read-only spec verification. Leave repository and tracker unchanged; keep scratch artifacts outside the repository. Return the complete QA report, checked commit, and retained evidence paths, including every fail and every blocked or untested required scenario. State whether coverage is complete.`
   - `Load and follow the code-review skill through the host's skill mechanism, with FIXED_POINT as the fixed point and REF as the spec.` Substitute the same resolved SHA and spec and include the fixed-point evidence and complete QA report. Append: `This is read-only spec verification. Leave repository and tracker unchanged; keep scratch artifacts outside the repository. Return the complete review report and checked commit, including every finding at every severity and the coverage of Standards, Spec, and Adversarial. List incomplete axes and unavailable independence honestly. Also return a separate blocking-gap list of every QA fail and verified P0 or P1 finding, and state whether both coverage sets are complete.`
   Follow the [harness contract](../../references/harnesses.md#invocation) for loading, including its installed-file fallback and unsupported-capability stop rule. QA and code-review are normal model-invoked dependencies, not additions to the user-invoked dispatch allow-list. This grants no additional user-only commands or external-peer consent.
3. Add every P2 or P3 finding from the complete review report to the friction log with its evidence. If either report is missing, any required QA scenario is blocked or untested, or any review axis is incomplete, park with the unresolved coverage; do not label the spec verified or close it. Only with complete QA and review coverage and no blocking gap, use the configured tracker's **Close** operation on REF with `Verified since <fixed point>: QA <verdict>, review <verdict>.` Re-read it to confirm closure.
4. With complete coverage and blocking gaps: for local Markdown acquire the tracker write slot first. Prompt `File one ticket per blocking gap as a child of REF, the way the configured tracker creates children, with acceptance criteria and the READY triage state. Reply with their numbers or canonical file paths.` (`--wait`) and wait for the worker. The spec now has open tickets, so the loop implements them, and the spec comes back here once they close. If this is the spec's second verification in this run that found gaps, park the lane instead of filing.
5. Apply [Remove the worktree](SKILL.md#lanes). Only after successful removal, drop its key from IN_FLIGHT. Report one line: `lane L: DISPLAY spec -> verified, closed` or `lane L: DISPLAY spec -> gaps <child references>`. On OMP append `phases <V history with each exact model handle and thinking, restarts included>` from the retained phase history; report no tier for a spec. Go back to Pick the issue.
