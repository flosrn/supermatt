# Run orchestrate in Tern

This run drives OMP workers in Tern panes instead of Herdr panes. Every procedure in this skill stays as written, with these substitutions for the whole run:

- **HERDR** is `node <this skill's directory>/scripts/tern-herdr.mjs`, with the directory as an absolute path, shell-quoted (`bun` may stand in for `node`). Every `herdr ...` command in SKILL.md, WORKER.md, ANSWER.md, SPEC.md, TRIAGE.md and LOCAL.md runs as `HERDR ...` with the same arguments. It answers in Herdr's JSON shapes and error codes, built on the `tern` CLI.
- **`$HERDR_PANE_ID`** and **`$HERDR_TAB_ID`** are both `$TERN_PANE`, your own block. `HERDR tab rename "$TERN_PANE" ...` renames your tab.
- **Workers are OMP only.** If the harness running this skill is not OMP, say that Tern serves only OMP workers, that Herdr runs the others, and stop.

## Setup in Tern

These replace the Herdr checks of Setup steps 1, 3 and 4; every other Setup step is unchanged.

1. Run `test "${TERM_PROGRAM:-}" = tern && test -n "${TERN_PANE:-}" && tern --version`. If it fails, say you are not inside a Tern pane and stop. Confirm access to the Tern daemon with `HERDR agent list`: a nonzero exit is a blocked operation, reported as in step 1.
2. Step 3's OMP checks: `HERDR agent start --help` must list `omp`, `HERDR integration status` must print an `omp: current` line, and `HERDR agent get "$TERN_PANE"` must return `.result.agent.agent` `omp`. If any of these fail, report it and stop.
3. Step 4: do not run `herdr --skill`. Follow the rules below instead.

## Rules

- Parse every ID from JSON output. Pane IDs are Tern block IDs. Never close a block you did not create.
- The shim absorbs transient daemon EAGAIN (`os error 35` or `Resource temporarily unavailable`) for safe-to-repeat reads only, with bounded backoff of about 60 seconds; `tern_failed` remains a real failure, and pane input is never retried. The `--timeout` of `agent wait`, of `agent start` (30 seconds by default), and of the wait `agent prompt --wait` does once omp has taken the prompt also ends the retries, and the command then returns `timeout`. Typing the prompt is not bound by `--timeout`: its reads keep the full retry budget, so a `timeout` from `agent prompt` always means omp took the prompt.
- `pane split` never takes the focus. `--ratio` has no Tern equivalent and is ignored, so stacked lanes split in halves instead of equal heights.
- Workers run omp's native renderer (`PI_TUI_NATIVE=1`), and `agent start` has each one record what it draws (`PI_TUI_TSP_RECORD`, a file under the shim's directory). Tern's own capture shows only the chat, so `agent read` prints that capture followed, as text, by what it leaves out: the working row, the composer's unsent text after `> `, a dialog in the composer's place, a sheet over the chat such as the plan review, and a full-screen view, with `›` on the highlighted option, `[x]` or `[ ]` on a check option, a question tab strip with `›` on the current tab, and each control's label and key hint in brackets, such as `[Submit  enter]`. `--source visible` and `--lines` work as in Herdr; `recent` and `recent-unwrapped` add the scrollback, both unwrapped, so Herdr's `agent_not_idle` refusal never happens.
- Agent states come from that record: a dialog, a sheet or a full-screen view waiting for input is `blocked`, the working row is `working`, a composer ready for a prompt is `idle`. `agent prompt --wait` and `agent wait` report `done` for an agent they saw work and then settle, as Herdr reports an unseen completion. A worker whose surface is suspended, or whose record is gone, reads `unknown`, and `agent prompt` and `agent wait` fail with `agent_state_hidden`: report it and park the lane. An omp that `agent start` did not launch, your own pane among them, has no record: it reads only `working` or `idle`, from Tern, and refuses `agent prompt`.
- omp holds its drawing back while Tern does not draw its pane, such as a pane in a tab out of sight, and sends it up to five seconds later. Each read waits for what omp held when the read started, so each read of such a worker can take about five seconds longer (`agent prompt` reads several times, so its cost compounds), and a worker started out of sight can take up to about fifteen seconds to start instead of one.
- `agent start` returns once the worker's composer can take a prompt. Its readiness poll tolerates a failed process query as not ready yet until `--timeout`; an inspect failure still fails the command. An omp that opens on a dialog returns `agent_not_ready` as soon as the dialog shows; the name is kept for `agent read` and `agent send-keys`. Before it launches omp it presses ctrl+u in the shell, one line per press and more presses than an orchestrate prompt has lines, so text a vanished omp never received is discarded instead of run; it sends no interrupt, which would cut a shell still loading its rc file.
- `agent prompt` refuses a blocked worker with `agent_blocked`, and a composer that already holds text with `agent_not_ready`, before it types anything. It pastes the text, waits for the composer to show it (a long paste shows as a chip such as `#1`), re-reads the worker, presses Enter, and waits for the composer to empty, which proves omp took the prompt. omp does both within a moment, but right after a turn it has taken five seconds, so each wait gives omp ten. A dialog before the Enter fails with `agent_blocked`, a worker showing no state with `agent_state_hidden`, an omp that left with `agent_not_found`, and a failed process query for a pane a fresh inspect still shows with `tern_failed` and Tern's message. Those refusals say whether the text sits unsent in the composer; a process query failure after the paste or Enter warns to read the pane before prompting again, never reports delivery. A paste that never shows, or text omp keeps after the Enter, is `agent_prompt_stalled`. Before prompting again, read the pane, and clear leftover text with `agent send-keys WORKER ctrl+u`, one line per press, until `agent read` shows no `> ` line. `--wait` keeps Herdr's gate: a worker that was not working must start working, open a dialog, or show the prompt as a user message or skill command card in its chat, or the prompt fails with `agent_prompt_stalled`, naming the gate it waited. The gate is 20 seconds for the first prompt an omp takes after `agent start` launched it, which may still be starting up, and five seconds for every later prompt; `--timeout` caps it, and a timeout that ends first is `timeout`.
- `agent send-keys` on a blocked agent returns once the dialog has closed, or after one second when the keys only move inside it, so the next `agent wait` does not read a closed dialog as `blocked`. Once it has sent its keys it succeeds, even when the answer leaves the worker without a state or ends omp, or a post-keys process query fails; the next call reports that. An inspect failure still fails the command.
- `.result.agent.agent_session` is `{"kind":"path","value":...}`: the OMP session file Tern reports for the worker.
- A name follows one omp process. Once Tern confirms a foreground other than omp or a different pid in its pane, the name is cleared with its record, and `agent get` returns `agent_not_found`: that is how you confirm a stopped worker has exited. A pane absent from inspect keeps its name, though that call also returns `agent_not_found`. If a process query fails and one fresh inspect still shows the pane, the call returns `tern_failed` with Tern's message and keeps both the name and its record; if the pane is absent from that inspect, it returns `agent_not_found` and keeps its name. An omp that has closed its surface on its way out already fails `agent prompt` and `agent wait` with `agent_not_found`. `agent start` also removes the records of workers that are gone.
- `agent read --format ansi` exits 2: Tern's ANSI capture leaves out what omp draws natively. A command or flag outside what `tern-herdr.mjs` serves exits 2 with the list of supported commands. Treat it as a failed Herdr control command (park the lane, or stop the run during Setup); never retry it against the real `herdr`.
