# Triage an issue (session T)

1. Show phase `triage`. Start the worker.
2. Prompt `/triage REF. I am away: where you would ask me, decide with the option you recommend. The goal is an agent brief and the READY triage state, unless the evidence says otherwise.` (`--wait`, no timeout) and wait for the worker. Its questions go through Answer a question: take the clear answer yourself, and use `/what-would-you-do` when the choice is not clear.
3. Read REF with the configured tracker's **Read an issue** operation; inspect state and labels, or `Closed:` and `Status:` for local Markdown.
   - Open with READY: if the queue tier at pick was `none`, send the same T worker the [Tier prompt](#tier-prompt) (`--wait`, no timeout) and wait. On OMP, after the attempt apply [Resolve the lane tier](SKILL.md#1-pick-the-issue), even when the prompt failed. For `light`, `standard`, `heavy`, or `invalid` at pick, send no tier prompt, even if `/triage` changed tier metadata; OMP keeps the pick's lane assignment. Then stop the worker and confirm its harness process has exited (its session stays in SESSIONS for the retro), and go on to Implement. Before Implement on OMP, any still-unset TIER takes the documented fallback.
   - Still TRIAGE: park the lane.
   - Anything else (closed, needs-info, ready-for-human, wontfix): add `DISPLAY triaged as <label or closed>` to the friction log, stop the worker, remove the worktree, drop its key from IN_FLIGHT, and go back to Pick the issue.

## Tier prompt

Use this single prompt for the READY outcome above and the [ready-only path](SKILL.md#1-pick-the-issue). It applies only to tickets whose queue tier at pick was `none`, never to specs. Substitute REF, the absolute tracker configuration path, and the configured LIGHT, STANDARD, and HEAVY strings before dispatch; include the lane's tracker ownership context from [LOCAL.md](LOCAL.md#worker-access-and-ownership) when local. T runs on its fixed row in [WORKER.md](WORKER.md), before a missing tier is resolved. Only OMP uses the resulting lane tier for later phase model and effort selection; other harness policies remain unchanged.

> Read REF using the configured tracker's Read an issue operation and the tracker configuration at CONFIG. Choose exactly one tier for this issue: light for a small, local, low-risk change; standard for normal work; heavy for a large, cross-cutting, or risky change. Use the corresponding configured string: LIGHT for light, STANDARD for standard, HEAVY for heavy. For GitHub, use Create a missing label before Apply label when the chosen label does not exist, then apply the chosen mapped label to REF. For local Markdown, set the Tier: metadata on the lane-owned canonical REF to the chosen mapped string; this edit needs no global tracker write slot. Keep the issue's triage state and other metadata unchanged. Use the configured Comment operation (Comment on an issue) to publish a one-line justification beginning exactly with `> *This was generated by AI during triage.*`, followed by the chosen tier and its reason. Do not implement the issue in this session.

Wait for the prompt to finish before stopping T and entering Implement. Every tier-prompt failure, including a failed dispatch or wait, tracker read, missing-label creation, tier application, or comment, continues to Implement; so does a missing resulting tier. On OMP, always re-run QUEUE after the attempt and resolve TIER and TIER_SOURCE through [Resolve the lane tier](SKILL.md#1-pick-the-issue); this includes the tracker-read evidence and friction entry when falling back to `standard`. Other harnesses keep no lane tier state and add no tier fallback entry. Do not retry tiering or make a resulting tier a new gate. These continuation rules concern the tier prompt only: worker launch, session-evidence, and stop/control failures outside that prompt, and non-READY triage outcomes, retain their existing handling.
