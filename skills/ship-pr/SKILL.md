Commit every change, push, open a pull request, and merge it once CI is green. Never commit onto the default branch. The arguments, if any, are a hint at what the change is about, not the message itself.

Keep a shipping record outside the worktree with the original and repair PRs, branches, checked commits, run IDs and attempts, logs, QA/review reports, and recovery counters. The original shipping operation and all its repair PRs share one set of recovery counters: initialize them only for a new shipping operation, and restore them from the record on continuation. Preserve the record across restarts and follow-up PRs.

Start from the session's working directory. When this session's work sits in another worktree (`git worktree list`), use that worktree as the execution cwd for every command and subprocess throughout shipping, CI recovery through `recover-ci`, and the [post-merge repair](CI.md), including `gh`, validation and hooks; leave the original working directory's changes untouched. `git -C <path>` scopes only that Git command, not subsequent commands. If the host cannot run hooks in the selected worktree, stop rather than run them from the original directory.

1. Run `git status --short --branch`, `git diff HEAD --stat`, `git log --oneline origin/HEAD..HEAD` (the branch commits), `git log --oneline -10`, and `gh api 'repos/{owner}/{repo}/actions/permissions' --jq .enabled` (whether Actions is enabled). Read the full diff (`git diff HEAD`), every untracked file `git status` lists, and, when there are branch commits, their diff (`git diff origin/HEAD...HEAD`) before writing anything. Read each issue the branch commits reference (`#N`) with the **Read an issue** operation in `docs/agents/issue-tracker.md`, since its comments hold the triage brief, or with `gh issue view N --json title,body,comments` when that file is missing.
2. Scan the working changes, untracked files, and every outgoing commit's content for credentials, tokens, private keys, and any value that does not belong in this repository. Inspect each commit relative to its parents, including root commits, merge resolutions, and values introduced then removed by a later commit; the net branch diff alone is insufficient because the push publishes intermediate history. Determine the outgoing commits against the destination remote's current refs. When delegating outgoing-history screening, the delegating session writes an evidence file outside the worktree beside the shipping record: record the destination remote's current refs and outgoing commit SHAs, then append two passes for every outgoing commit. The record pass is the full output of `git show --format=fuller --root --diff-merges=separate -p --binary --no-ext-diff --no-textconv <sha>`, which includes root patches and separate diffs against every merge parent, exposing merge resolutions and transient secrets instead of only the net diff. The readable pass runs the same command with `--text` in place of `--binary`, so a file that a `-diff` or `binary` attribute reduces to an encoded binary patch in the record shows its contents; save each readable output to a temporary file, check that `git show`'s own exit status is zero, then append it with NUL bytes removed (`LC_ALL=C tr -d '\000'`, since a UTF-8 locale makes `tr` reject non-UTF-8 bytes) so the evidence file stays text. Confirm ref discovery, commit enumeration, every `git show`, and every `tr` succeeded and the file contains all output without truncation before delegating; failed or incomplete collection blocks screening and shipping. Pass the file path to the read-only reader, which reads that evidence rather than running git and names every path the record marks binary whose readable pass it could not screen as text. The delegating session screens each named blob itself before shipping; a blob that nobody screened blocks shipping. If you find a secret anywhere in that content, stop, commit and push nothing, and report it without exposing the value. Do not rewrite history automatically.
3. If the current branch is the repository's default branch, create and switch to a new one first: `type/kebab-description`, where `type` matches the Conventional Commit type you are about to use and the description comes from the change itself. Any branch commits move to the new branch with it: then run `git branch -f <default> origin/<default>` so the default branch matches its remote and the merge can fast-forward it.
4. Stage the changes. Prefer explicit paths over `git add -A`. An untracked directory that holds a local tool's state (an index, cache, or database, such as `.codegraph/`) belongs in the root `.gitignore`, even when it ships its own `.gitignore`: add its path there, stage that line with the rest, and say so in the report.
5. If staged changes exist (`git diff --cached --quiet` exits 1), write a Conventional Commit `type(scope): description`, matching the subject style already in `git log`, and commit them. When the `oss-writing` skill is installed, load and follow it through the host's skill mechanism for the wording. With no staged changes, keep the existing commits and continue without an empty commit. Any other exit status is an error to resolve, not an empty index.
6. Run `git push -u origin HEAD` with a 10-minute timeout: a pre-push hook can run the whole test suite. The outgoing-history screening in step 2 applies even when no new commit was needed. If the hooks must run against a scratch copy, complete the [scratch dependency preflight](../../references/scratch-dependencies.md) in that exact copy before pushing. Use the normal unchanged hooks, launched from the selected shipping worktree.
7. Create the PR with `gh pr create`, or update the existing PR for this branch after a repair. The title and body cover the whole branch: your commit's subject when it is the branch's only commit, otherwise one Conventional Commit subject spanning every commit. With a squash merge, the title becomes the one commit on the default branch. Use the repository's pull request template when it has one. Otherwise, load and follow the `pr` skill through the host's skill mechanism for the body, and load and follow `oss-writing` for the wording when that skill is installed, even when no commit was written in step 5. When the repository documents a **Merge** operation in `docs/agents/merge.md`, start it immediately after creating or updating the PR, without waiting for CI: follow its enqueue instructions now, and let the merge train wait for its Merge Gate. For repositories supporting the conflict marker below, register each original or repair PR's owner and caller coordinator and arrange the [durable conflict handoff](#durable-conflict-handoff) before settling into the wait. Report the PR, merge request and handoff route to the caller; creating or labelling a PR is not completion. Continue monitoring CI in step 8 while the train owns the merge.
8. Inspect applicable PR checks and commit statuses at the exact head, including external CI, and use `gh pr checks --watch` until they settle. It exits non-zero on failure, so allow that and read the result. Actions enabled `false` means only that GitHub Actions is disabled; external checks and statuses may still apply. If no checks appear, wait 20 seconds and query again. Percent-encode the base branch as one URL path parameter (`/` becomes `%2F`) and use that encoded value for `<base>` in both lookups: read branch protection's required checks with `gh api 'repos/{owner}/{repo}/branches/<base>' --jq .protection.required_status_checks` (available on every plan), and rulesets with `gh api --paginate 'repos/{owner}/{repo}/rules/branches/<base>'`, inspecting every page it returns: the endpoint pages its results, and several repository and organization rulesets can apply to one branch. A rulesets 403 whose message says to upgrade to GitHub Pro or make the repository public establishes that rulesets do not apply on this plan, not unavailable configuration; do not retry it with the `/protection` or `/rulesets` endpoints. Report no CI only when repository configuration and required-check settings establish that none applies. A missing expected check or genuinely unavailable configuration (any other failure) is blocked, not green.
9. When `docs/agents/merge.md` documents the **Merge** operation, wait for the train to merge the PR instead of calling `gh pr merge`. Follow that operation's wait and stop conditions, including ejection, holds and conflicts; enqueueing is not a completed merge. With durable conflict handoff active, let its background watcher deliver conflicts rather than starting model sleep/tick turns; it does not replace step 8's checks or the repository's full merge wait. On an event, re-read the current head, labels and trusted marker before acting. Under `orchestrate`, request the ship slot and return through its Sync and QA/review safety gates. Re-sync using the repository's published-branch safety rules: merge current main where rewriting is not authorized, and lease any authorized rewritten push against the recorded remote head. A notification grants no force-push permission. Keep ownership recorded until independently confirmed MERGED, including when this worker returns or restarts; an unavailable owner hands responsibility to the coordinator, not to nobody. Without supported event delivery, report that gap and retain the full existing wait path. When that file is missing, merge on green checks with `gh pr merge <PR URL> --squash --match-head-commit <checked-head>`, where `<checked-head>` is the head SHA step 8 checked. Then confirm `gh pr view <PR URL> --json state,mergedAt` reports MERGED and read the merge SHA from `gh pr view <PR URL> --json mergeCommit --jq .mergeCommit.oid`. Keep the branch and worktree while this worker is alive: shell `cd` does not move the harness or its hooks out of their working directory. The orchestrator removes its clean worktree after the worker exits; a standalone run offers safe cleanup in step 13, retaining its active worktree for its caller. On a failed check, load and follow the `recover-ci` skill through the host's skill mechanism, passing the PR URL, the checked head SHA, and the recovery counters from the shipping record, with the record as the place each spend is written. Record its outcome and evidence, then return to the CI gate for the repaired head. Merge only with all required checks green on that exact head, and preserve branch protections. A `stopped` or `budget-exhausted` outcome leaves the PR unmerged with its evidence and remaining blocker.
10. Merged: close each issue the branch commits reference (`#N`, or a local issue path) that is still open, since the merge is what finishes it and a closed issue unblocks the tickets that wait on it. Use the **Close** operation in `docs/agents/issue-tracker.md` with the comment `Merged in <PR URL>.`, or `gh issue close N --comment` when that file is missing.
11. Verify the CI and deployment workflows triggered by this merge before reporting completion. Resolve the merge SHA and identify applicable workflows from repository configuration, including chained workflows; use `gh` to inspect runs for that exact commit. Wait for them to settle. If an expected run has not registered, wait 20 seconds and query again; a still-missing expected run is blocked, not success. Record intentionally filtered/skipped workflows or no configured post-merge workflow separately. A failed run follows the [post-merge repair](CI.md), which recovers it through `recover-ci`. A pending approval or unavailable external service stays blocked without bypass. Follow the caller's ship-slot scope: `orchestrate` has released it after opening the PR, so post-merge verification does not hold it. Report a failed or blocked default-branch run immediately so the caller can hold further merges.
12. Report every original and repair PR URL and merge SHA, issues closed, CI outcomes and remaining coverage gaps, recovery counters, retained branches, and the shipping record path. Distinguish a successful original merge from blocked post-merge verification. Report the `.gitignore` line from step 4 if one was added.
13. Only after a verified merge and successful post-merge verification (or an explicit record that no post-merge workflow is configured), offer cleanup when `command -v tern-wt` succeeds. Under `orchestrate`, defer this offer to the coordinator's **On stop** step, after its parked-lane report, rather than asking inside the running loop. For a standalone run, resolve the main checkout from `git worktree list`, then run `tern-wt clean --repo <main checkout>` as a dry run. Summarize its JSON `remove` lists (worktrees, branches, processes, containers, and paths), `keep` entries with their reasons, and `warnings`. If the active shipping worktree appears in `remove`, report the mismatch and do not apply: the harness and its hooks still need it. Ask: "Shipping is verified. Apply this cleanup plan?" Only after the user says yes, run `tern-wt clean --repo <main checkout> --apply`; it recomputes the plan. Report what was removed, what was kept and why, and any warnings or per-item failures. Without approval, leave everything unchanged. Let `clean` preserve the main checkout, work to lose, the calling process and its ancestors, unrelated live Tern blocks, and shared service containers; never force their removal or replace the command with manual deletion.

## Durable conflict handoff

Use this path when the repository's merge instructions support `<!-- merge-train:conflict <full-head-sha> -->`. Set `SKILLS` to the absolute installed skills root, `REPO` to `gh repo view --json nameWithOwner --jq .nameWithOwner`, `PR` to the PR number, and `TRAIN_LOGIN` to the trusted author's exact login from those instructions, for example `acme-merge-train[bot]`. Never infer trust from a comment's author. Choose `MERGE_TRAIN_STATE` once per repository, defaulting to `${XDG_STATE_HOME:-$HOME/.local/state}/supermatt/merge-train/OWNER/REPO` with actual owner/repository components. Reuse the caller's directory outside every worktree, shared across lanes and restarts.

On Tern, resolve the local shipping block as `OWNER` and the explicitly supplied caller block as `COORDINATOR` through `tern-sessions list --json`, never branch guesses. Registration pins pid/session file; re-register replacement sessions. Supply aliases only for live agents the shim can prompt:

```sh
node "$SKILLS/ship-pr/scripts/merge-train-watch.mjs" register \
  --repo "$REPO" --state "$MERGE_TRAIN_STATE" --train-login "$TRAIN_LOGIN" --pr "$PR" \
  --owner "$OWNER" --coordinator "$COORDINATOR" \
  --owner-agent "$OWNER_AGENT" --coordinator-agent "$COORDINATOR_AGENT"
```

Omit unavailable alias flags and standalone coordinator flags. Both commands require the same explicit `--state` and `--train-login`; state pins the repository/login and rejects mismatches. Record registration and the host's watcher handle beside the shipping record. Prefer a coordinator-owned background job with no deadline, whose result starts its next turn:

```sh
node "$SKILLS/ship-pr/scripts/merge-train-watch.mjs" watch \
  --repo "$REPO" --state "$MERGE_TRAIN_STATE" --train-login "$TRAIN_LOGIN" \
  --coordinator "$COORDINATOR" --coordinator-agent "$COORDINATOR_AGENT" \
  --interval 60 --until-event
```

Launch from a stable directory through the host's background-job mechanism, not shell `&` or a new service installation. On OMP, use a background Bash job with `async: true` and `timeout: 0`. `--until-event` polls outside the model, prints a conflict batch or failure as JSON, then exits; the host result wakes this coordinator even with inbox off. Revalidate and handle a successful batch under step 9, then re-arm the same command. Exit 1 reports a read/delivery blocker: resolve it before re-arming, rather than creating immediate failure turns. Retain the handle/logs outside the worktree and restore the watch after coordinator restart. Exactly one process holds the state lock; a lock refusal proves no coverage. Startup scans all open `merge`-labelled PRs, including orphans, and zero PRs alone does not stop the job.

For continuous transport without a host-result wake, omit `--until-event`. Use the host's named persistent process mechanism; on OMP, a named Bash service with readiness `"event":"ready"`, then `proc://<handle>/mode` set to `persist`. Check its ready repo/state/coordinator and reuse only a live matching watch. Mere liveness does not wake a coordinator; inbox/alias delivery below or operator action must do that. If a standalone shipping session ends while this process lives, route its vanished owner to the registered coordinator, otherwise operator notification. If the process stops, monitoring stops: relaunch explicitly. State survives process restart, but neither mode installs a daemon or reboot supervision.

GitHub polling runs outside the model. Only an exact `<!-- merge-train:conflict 40hex -->` from `TRAIN_LOGIN` for the full current head of an OPEN, `merge`-labelled PR triggers delivery. A hold suppresses it until a later trusted `<!-- merge-train:approved <candidate-sha> -->` matches the held candidate; the label alone proves no approval. Stale markers are ignored and comment text is never executed. Atomic ownership/delivery records survive restart without clobbering each other. Deduplicate repository/PR/full-head only after transport succeeds; failures stay pending and a new head is a new event.

Try owner, coordinator, then operator. Primary transport is `tern-sessions send BLOCK TEXT --from supermatt-merge-train --json`, only with `canReceive` and existing `trustedSenders` opt-in. A registered live shim agent may fall back to `node "$SKILLS/orchestrate/scripts/tern-herdr.mjs" agent prompt NAME TEXT` without `--wait`, checking its exit. This cannot prompt a coordinator started outside the shim; never use raw pane typing. Otherwise run `node "$SKILLS/orchestrate/scripts/tern-notify.mjs" --pane BLOCK "Merge train conflict" "BODY"` for the coordinator, else originating `TERN_PANE`. Notifications alert the operator, not an agent turn. Mailbox success also proves transport, not completed resolution. Report missing/failed routes.

Read [Tern inbox adoption](../orchestrate/TERN.md#conflict-event-delivery): an installed CLI, `inbox: off` or user-confirmed delivery does not prove unattended mailbox coverage. The coordinator's own `--until-event` host result needs no inbox restart; cross-session inbox wake still needs the opt-in. Never change user trust configuration. Without Tern, a usable host background mechanism or delivery route, report `conflict event delivery unsupported: <reason>` and retain the repository's full checks and merge wait.

Replace `--until-event` with `--once --dry-run` for JSON route plans after one tick, without sends, state mutation or a retained lock. A plan is not delivery evidence.
