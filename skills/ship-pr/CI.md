# Post-merge repair

Use this procedure when a CI or deployment workflow triggered by the merge fails. The diagnosis, rerun, repair, and verification belong to `recover-ci`; this procedure owns the repair branch, the merge hold, and the follow-up PR around it. Its counters are the shipping operation's, from the shipping record.

The original PR remains merged and its issue remains closed. Keep that outcome separate from recovery; do not rewrite the default branch or reuse the merged feature branch for a repair.

1. Record the failed merge SHA and notify the caller to hold further merges. Fetch the current default branch and, with a clean worktree, create a new `fix/ci-<failure>` branch from `origin/<default>`. The current worker can switch to this branch in its existing worktree; do not remove a worktree while its harness is alive. Record both branch names for later cleanup. Respect the caller's resource assignments before any reproduction or test. Then load and follow the `recover-ci` skill through the host's skill mechanism, passing the merge SHA, the failed run, the repair branch, and the recovery counters from the shipping record, with the record as the place each spend is written. A transient failure ends at its rerun, and the unused repair branch is reported for cleanup.
2. Once `recover-ci` returns `repaired`, open a follow-up PR that links the original PR and failed run and explains the observed failure. Use normal review, hooks, required checks and the merge procedure in steps 7 through 9 of [ship-pr](SKILL.md); do not push directly to the default branch. A failed check on that PR goes back to `recover-ci` with the same counters. A `stopped` or `budget-exhausted` outcome, or a repair that needs another product decision or broader permissions, stops with that blocker.
3. Verify the repair merge's applicable CI and deployment workflows at its exact SHA. Keep the shared counters across any further repair PR. Release the merge hold only when those workflows succeed, or when configuration establishes that no such workflow applies. If the default branch advances externally, verify the current tip as well before clearing the hold; superseded or cancelled runs are not a passing result. On exhaustion or an external blocker, retain the hold and report the original merge plus the unresolved recovery separately.
