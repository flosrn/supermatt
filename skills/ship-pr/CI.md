# CI recovery

Use this procedure for a failed PR check or a CI/deployment workflow triggered by a merge. It applies to repository defects exposed by the run even when the shipped diff did not introduce them. Keep the repair limited to the observed failure and preserve the user's scope and permissions.

## Budget and evidence

The original shipping operation and all its repair PRs share **two repair cycles** and **one transient rerun**. Initialize unused counters only for a new shipping operation; restore existing counters from the shipping record on continuation. Recover its path from the caller or prior session before resuming an existing PR or post-merge repair. If the prior attempts cannot be established, stop with that evidence gap instead of assuming a fresh budget. A new commit, failure, PR, worker session, or post-merge run does not reset them. Increment a repair cycle before editing; it includes the fix, verification, push, CI and any resulting post-merge check. An unexpected local verification failure or a review finding returns to diagnosis and consumes the next cycle before further edits; an intentional red regression reproduction is part of the current cycle. Retain each failed attempt instead of replacing its logs with a later pass.

Stop when the applicable budget is exhausted, the cause cannot be established from available evidence, required access is unavailable, or the fix needs an unresolved product decision. Report the failing run and step, diagnosis and uncertainty, attempted repairs, checked commits, and the exact blocker. An unattended caller parks the lane; a standalone caller receives the same handoff. A protected approval is a blocker, not permission to change access or bypass it.

## Diagnose and recover

1. Read the failed job logs and inspect the implicated source, workflow, and environment. Record the run ID, attempt, commit and failing command. Distinguish a repository defect from a transient service/runner failure or an access/approval problem. A red check alone is not evidence of a transient failure.
2. For a supported transient failure, spend the remaining transient rerun on the failed jobs of that exact run (`gh run rerun <run-id> --failed` for Actions). Wait for the new attempt to settle and record its result. If it fails again, diagnose the new evidence; repair an established repository defect within the remaining repair budget, otherwise stop. Do not rerun assertion failures merely to obtain a green result.
3. For an established repository defect, spend the next repair cycle. For an already merged PR, use the post-merge procedure below first. Pin the pre-fix commit. For a behavior-changing repair, load and follow the `tdd` skill through the host's skill mechanism before editing. Make the smallest fix on the existing PR branch. Where a regression check can prove the failure, reproduce it before the fix and verify it afterwards. Keep checks and protections effective: do not skip tests, loosen assertions, remove required checks, or disable protections merely to get green CI. A defective assertion can be corrected only with independent evidence of the intended behavior and a check that still rejects the wrong behavior. Complete the repository's required local gate, then repeat `ship-pr`'s step 2 screening of working changes, untracked files, and outgoing history before committing. A detected secret stops both commit and push without rewriting history. Otherwise commit the fix with normal hooks before follow-up QA and review.
4. After committing the repair, run affected checks, then load and follow the `qa` skill through the host's skill mechanism for affected behavior, then load and follow the `code-review` skill through the host's skill mechanism on the repair commits against the pre-fix commit. A test-only repair needs affected tests and independent follow-up review, not browser QA of unchanged runtime code. Each later review round uses the previous reviewed commit as its fixed point. Carry forward only evidence whose relevant source, dependencies, configuration and environment are unchanged. Give the reviewers the failure evidence and prior reports. Every verified finding or QA failure must be resolved within the remaining repair budget; follow-up verification does not grant extra cycles. Preserve independent review even for a test-only fix.
5. After follow-up verification passes and no verified finding remains open, repeat `ship-pr`'s step 2 screening against the destination remote's current refs, including every new repair commit and any secrets later removed. If it finds a secret, stop without pushing or rewriting history. Otherwise push the checked repair commits with normal hooks. Update the existing PR, or create the post-merge repair PR. Return to `ship-pr`'s CI gate and wait for all checks on the new head. A previous head's green CI cannot authorize this merge. On failure return to diagnosis with the counters intact.

## Post-merge repair

The original PR remains merged and its issue remains closed. Keep that outcome separate from recovery; do not rewrite the default branch or reuse the merged feature branch for a repair.

1. Record the failed merge SHA and notify the caller to hold further merges. Fetch the current default branch and, with a clean worktree, create a new `fix/ci-<failure>` branch from `origin/<default>`. The current worker can switch to this branch in its existing worktree; do not remove a worktree while its harness is alive. Record both branch names for later cleanup. Respect the caller's resource assignments before any reproduction or test.
2. Make and verify the repair through the shared procedure above. Open a follow-up PR that links the original PR and failed run and explains the observed failure. Use normal review, hooks, required checks and squash merge; do not push directly to the default branch. A repair that needs another product decision or broader permissions stops with that blocker.
3. Verify the repair merge's applicable CI and deployment workflows at its exact SHA. Keep the shared counters across any further repair PR. Release the merge hold only when those workflows succeed, or when configuration establishes that no such workflow applies. If the default branch advances externally, verify the current tip as well before clearing the hold; superseded or cancelled runs are not a passing result. On exhaustion or an external blocker, retain the hold and report the original merge plus the unresolved recovery separately.
